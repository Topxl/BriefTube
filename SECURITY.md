# Security Policy

BriefTube is open source, and the same codebase runs the hosted service at
<https://www.brief-tube.com>, which holds real user accounts, Telegram chat identifiers
and Stripe customer records. A vulnerability here is not theoretical, so please report it
privately rather than opening a public issue.

## Supported versions

| Version                | Supported |
| ---------------------- | --------- |
| `main` (latest commit) | Yes       |
| Anything older         | No        |

There are no release branches and no backports. Fixes land on `main`; self-hosted
operators are expected to track it. The hosted service always runs a recent `main`.

## Reporting a vulnerability

**Report through GitHub Security Advisories:**

<https://github.com/Topxl/BriefTube/security/advisories/new>

That form is private, visible only to the maintainer, and lets us discuss and prepare a
fix before anything becomes public. It is the only supported private channel — please do
not use public issues, discussions, pull requests, or the in-app support chat for
security reports.

If you cannot use the form for some reason, open a public issue that says only "I would
like to report a security issue privately" with no technical detail, and you will be
invited to a private advisory.

### What to include

The more of this you can provide, the faster the fix:

- The affected component: web app, worker, Telegram bot, one of the other delivery
  channels, the browser extension, or the hosted service specifically.
- The commit SHA you tested against, or "hosted service" plus the date and time.
- A description of the impact — what an attacker gets, not just what is wrong.
- Reproduction steps, or a proof of concept.
- Any suggested fix, if you have one in mind.

## Response times

Set your expectations honestly: this project is maintained by one person in their spare
time, and is in light maintenance. Security reports are the one category that still gets
priority, but the timeline is measured in days and weeks, not hours.

| Stage                                                 | Realistic target                    |
| ----------------------------------------------------- | ----------------------------------- |
| First acknowledgement                                 | Within 7 days                       |
| Initial assessment (severity, whether it reproduces)  | Within 14 days                      |
| Fix for a critical issue affecting the hosted service | As fast as possible, typically days |
| Fix for everything else                               | Best effort, no commitment          |

If you have had no reply after 14 days, the report was probably missed rather than
ignored. Open a public issue saying only that a private report is awaiting a response,
with no technical detail, and it will be picked up.

## Disclosure

Coordinated disclosure. Please give a reasonable window before publishing — 90 days is
the default assumption, shorter by mutual agreement once a fix is out. Reporters are
credited in the advisory and in `CHANGELOG.md` unless they prefer to stay anonymous.

There is no bug bounty. Nothing is paid for reports.

## Testing against the hosted service

Testing against your own self-hosted instance is always fine. Against
`brief-tube.com`, keep it to accounts you own and to non-destructive probing.

Do not:

- Access, modify or exfiltrate data belonging to other users.
- Run automated scanners, fuzzers or load tests against the production host.
- Perform denial-of-service testing, or anything that degrades the service for others.
- Use social engineering or physical attacks against the maintainer or third-party providers.

Reports that follow those limits will not be met with legal action.

## Out of scope

These get closed without a fix, unless you can show real impact:

- Missing security headers or TLS configuration nits with no demonstrated exploit.
- Vulnerabilities that only apply to a misconfigured self-hosted deployment — for example
  exposing the worker's HTTP port (`:8080`) or Supabase service-role key to the internet.
  That port and that key are trusted by design and must stay on a private network.
- Rate-limiting and abuse concerns on a self-hosted instance you control.
- Vulnerabilities in third-party services (Supabase, Stripe, Vercel, Telegram, Modal,
  Cloudflare) — report those to the vendor.
- Reports generated by a scanner with no verification that the issue is real.

## A note for self-hosters

The repository ships templates, never real credentials. When you deploy your own instance
you are responsible for the secrets you create: `SUPABASE_SERVICE_ROLE_KEY` bypasses row
level security entirely, `TELEGRAM_BOT_TOKEN` gives full control of your bot, and Stripe
keys move money. Keep them out of git, out of client bundles (only `NEXT_PUBLIC_*`
variables belong there), and rotate them if they ever leak.
